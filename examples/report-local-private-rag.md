## Hybrid Search Implementation

Hybrid search combines keyword matching (BM25) with semantic vector search to get both exact-term precision and meaning-based recall in a single retrieval step [E11]. Pure vector search misses exact matches such as product SKUs, error codes, CVE IDs, and person names because dense vectors compress away token-level information [E11]. Conversely, pure keyword search misses paraphrases like when "rate limit exceeded" does not match a document saying "too many requests per minute" [E11]. Retrieval quality acts as the ceiling for RAG answer quality because if the right document isn't in the top-k results, no LLM can produce a correct answer [E11]. To resolve this, hybrid search solves both problems by running both retrieval methods in parallel and merging results [E11]. Score fusion merges ranked lists from both retrievers using reciprocal rank fusion (RRF), weighted averaging, or learned models [E11]. RRF is the safest default for fusing incompatible scores without tuning [E13].
Implementation often uses frameworks like LangChain hybrid retrievers or LlamaIndex BM25 + vector codified patterns [E15]. Hybrid search executes sparse retrieval (BM25) scoring by term frequency and inverse document frequency, which is fast and exact without GPU requirement [E15]. Dense retrieval scores documents by embedding cosine similarity or dot product to capture semantic meaning and paraphrases [E15]. Most deployed systems use alpha parameter values between 0.6–0.75 favoring vector, adjusting based on retrieval evaluation on real queries [E15]. The 2021 BEIR benchmark showed dense retrieval losing on keyword-heavy corpora while hybrid consistently topped either method alone [E15]. Frameworks like Weaviate, Qdrant, Pinecone, Milvus, and Elasticsearch 8.x ship hybrid query APIs natively [E11]. Postgres with pgvector and full-text search is another implementation option requiring careful chunking [E10]. Teams that deploy vector-only search consistently hit a wall when users search for exact identifiers and get semantically related but wrong results [E11]. Users paraphrase queries ("how to fix connection issues") and keyword-only search returns irrelevant exact matches on common terms [E11]. Implementing hybrid in Postgres with pgvector allows handling the exact error code and the vaguely-phrased question equally well [E10].
Dual indexes typically increase storage over vector-only, though exact overhead depends on sparse index size [E12]. Both indexes scale horizontally in Qdrant, Weaviate, and Milvus for dual-indexed setups [E12]. Parallel search adds minimal latency as total retrieval is dominated by the slower path rather than their sum [E12]. Illustrative combined retrieval often runs at \~30–150ms depending on hardware, corpus size, embedding model, and vector database [E12]. Latency for hybrid search can be higher compared to vector-only due to the extra processing steps [E14]. No additional API costs for BM25 exist since it is compute-only, though embedding costs remain unchanged [E12]. There is slightly higher storage cost associated with maintaining dual indexes [E12]. Query and documents must use the same model or vectors are not comparable [E13]. Bad chunking dominates vector quality before blaming the model, as chunk size and boundaries affect performance significantly [E13]. Blending raw BM25 and cosine scores is incompatible due to scale differences [E13]. Vector returns confident nonsense when it always returns nearest neighbors without an honesty check from thresholds [E13]. Mismatched embedding models prevent vectors from being comparable across query and documents [E13].
Evaluation requires A/B testing vector-only vs hybrid on a golden set weekly to benchmark on production-like workloads [E12]. BEIR and other published hybrid results are useful for comparison but should not replace evaluation on production-like workloads [E12]. The merged result set feeds into downstream stages — metadata filtering, reranking, generation — with better recall than either method alone [E15]. Hybrid search is not a replacement for ANN indexes or reranking — it sits between embedding and precision layers in the retrieval stack [E15]. Vector search matches meaning but misses exact tokens and sometimes returns confident nonsense [E10]. Keyword search matches exact words while missing meaning [E10].

## Local Reranking Mechanism

A re-ranker is a model that takes a query and a candidate document together and produces a relevance score [E18]. Because it sees the pair jointly, it can score relevance much more sharply than an embedding model which processes them separately [E18]. Three options you will see are Cohere Rerank, BGE rerankers, and Voyage Rerank [E18]. Cohere Rerank is hosted as an API while also supporting multilingual capabilities [E18]. BGE rerankers are open-source and free to self-host [E18]. Voyage Rerank offers specialized variants for different domains via hosting [E18].
The latency penalty is typically 100–400ms for 25–50 candidates during the re-ranking process [E18]. This delay occurs because most production RAG systems report a 10–30% improvement in answer quality after adding re-ranking [E18]. Recall improvement is usually large enough to be worth it, though diminishing returns are observed past that threshold [E18].
Standard cosine similarity searches sometimes retrieve chunks that share keywords but lack semantic intent [E19]. A solution involves using a lightweight local cross-encoder model to reorder candidate passages before generation [E19]. This optional reranking step is not implemented in the code above, but it can be added manually [E19].
For local deployment on an 8GB GPU, checking total VRAM requirement is necessary because a 7.5 GB GGUF file does not mean 7.5 GB of VRAM [E17]. The FP16 KV cache at 32K context adds another 1–2 GB depending on architecture [E17]. Full GPU offload is non-negotiable on 8GB to avoid performance penalties [E17]. Even 4 layers spilling to CPU cuts decode speed by 70% [E17].
Qwen3.5-9B is the benchmark to beat until a sub-10B model surpasses it on the AA Intelligence Index while maintaining full GPU offload at 32K on 8GB VRAM [E17]. One area where this class of models genuinely shines is long-document workflows like RAG [E17]. Regarding hardware constraints, an 8 GB GPU remains useful for local inference but is best treated as a small-model tier [E25].
