### 1. The product

**A local research assistant that builds you a knowledge base you own.**

- **Research:** give a goal; it plans with you, reads a bounded set of the
  best sources, and writes a report where every claim traces to a quote,
  names its real subject, is labelled by evidence strength, and says plainly
  what the evidence cannot answer.
- **Chat:** ask questions of your library in conversation; answers are cited,
  state what the library covers, and hand off to a full report when a
  question needs real synthesis.
- **Compounding knowledge:** every run adds checked sources and facts to a
  topic collection, so later chats and reports get faster and better, and
  work offline from what you have collected.

Runs fully locally (Ollama, no paid APIs, no cloud) on one laptop
(8 GB GPU, 24 GB RAM). Quality over speed: a report may take hours.

**First a good research assistant (Phase 1). Chat, compounding and domains
follow, but Phase 1 stores data so they need no rework.**

**Useful to the user first; then a private-first deep research product.**
The same system is later shown to clients as a demo or prototype: their
own documents plus the web, everything on their machine, every answer
traceable to a source. Client work (private sources, sign-in, per-user
access) is backlog until a real client asks; Phase 1 only records each
source's origin so it can be added without rework.

### 2. In and out

| In | Out |

### 4. Architecture

```
                         ┌───────────────── LIBRARY (one per user) ─────────────────┐
  Collect (online) ───►  │ Collections (per research topic)                          │
  Add URL / PDF    ───►  │   Sources (tier, version-merged, deduped, dated)          │
                         │   Passages (hybrid index: FTS5 + vectors)                  │
                         │   FACT BANK (verified, structured, cited, reusable)        │
                         └──────────────▲──────────────────────────────▲─────────────┘
                                        │                              │
   RESEARCH (big model)                 │        CHAT (fast model)     │
   goal → clarify → plan → coverage ────┘        question → retrieve passages + facts
   → approve plan + rules → collect wide         → cited answer + coverage statement
   → index ALL → rank → read best per question
   → verify → select ≤80 facts → write           → "make this a report" ──► RESEARCH
   → critique → revise → checks → report         (collect off by default)
   → new facts saved to the fact bank
```

### 5. Collect wide, index everything, read the best, use a few

A run handles sources at four levels, each cheaper and wider than the next:

| Level | What happens | Cost | Bound |
|---|---|---|---|
| **Found** | Search results for the plan's questions | Seconds | Collection rules (source types, sites, dates) |
| **Collected + indexed** | Fetched, converted, split into passages, embedded into the topic collection | No LLM; minutes (PDF conversion is the slow part) | L2 safety cap only |
| **Read** | The research model extracts and checks structured facts → fact bank | Hours | L3, L4 |
| **Used** | Facts in the report | One 32k context | L6, L7 |

Nothing collected is wasted: unread sources stay searchable by chat and are
the starting point of the next run on the topic. The user approves the
**plan and the collection rules**, not each source; a candidate list stays
available to exclude sources but is optional. Ranking for reading uses
relevance to the question, source tier and novelty.

**Source states** (stored per source, per collection): `indexed` (passages
only, unchecked) → `read` (facts in the fact bank) → `used` (in a report).
Chat and reports say which state their evidence comes from.
**Source origin** (stored per source): `web`, `upload`, later `connector`.

#### Run limits (assumptions, checked in the model test)

The model never reads whole PDFs and never reads all documents at once.
Reading is limited by **time** (separate small calls); writing is limited by
**context** (one call holding all selected evidence).

| # | Limit / assumption | Value |
|---|---|---|
| L1 | Questions per report | 3-4 |
| L2 | Sources collected + indexed per run | no ticking; safety cap ~300 (time and disk) |
| L3 | Sources read per question | ≤ 12 |
| L4 | Sources read per run | ≤ 50 |
| L5 | Read from a source, per question | best 3-4 passages (~3k tokens) |
| L6 | Facts per source in the final evidence | ≤ 4 |
| L7 | **Facts in the writing step** | **≤ 80** (~20k tokens at ~200 per fact) |
| L8 | Sources that shape a report | ~20-25 |
| L9 | Library size | no hard limit |
| L10 | Time per report | ~3-5 h (estimate; measured in the test) |

All limits live in configuration, are shown in Settings, and anything left
out is listed in the run log and the report ("collected 286, read 47,
used 23; 239 indexed for later").

### 6. Fact format

**Core (every domain):**
`subject` (what the source is actually about, in its own terms) · `claim` ·
`quantity` + `unit` (optional) · `conditions` (setting, dataset, date) ·
`quote` (verbatim) · `source_id` · `passage_id` · `collection` · `checked`
(quote, support, subject) · `created_run`.

**AI/ML pack fields:** `system` (model/method name) · `size` (params) ·
`stage` (pretraining / continued pretraining / fine-tuning / post-training /
inference) · `task` · `dataset` · `metric` · `hardware`.

Subject check: a claim may only use size/stage/system terms present in its
passage's fields. "Pretraining a 4B model" from a 17B fine-tuning card fails
on `size` and `stage`, by comparison, not by judgement.

### 8. Acceptance tests (definition of done)

**Phase 1a-0**
- ~50 claims labelled by stage; error breakdown in `EVALS.md`; scoreboard has v6 and raw-passage baseline columns.
- Mini fixture runs end to end in < 10 min; writing replays from saved evidence.
- Code-audit decision recorded.

**Phase 1**
- Every structured stage added in 1b/1c beats the raw-passage baseline on the scoreboard, or is cut.
- Critique → revise kept only if it raises the blind score.
- The claim check view opens the highlighted quote for any claim in one click.
- Portfolio deliverables and pre-publish clean-up done.
- The known bad cases (E7/E8 post-training → "pretraining from scratch", E79 17B card → "4B pretraining", E76/E40 fine-tuned card) are caught by tests.
- 0 subject violations in a 30-fact random sample (manual check).
- 100% of numbers in summary and decision trace to a single fact.
- No "established" label on a stitched or single-source claim.
- Summary/decision overlap < 50%.
- Every run log shows collected / read / used counts; every collected source is in the collection's index; no prompt over its budget.
- Chat preview answers 10 questions over a collection with citations, marks unchecked evidence, and refuses 2 out-of-library questions.
- 3 gold goals (T1-T3) produce reports judged better than the v6 baseline on the blind checklist (subjects, numbers, decision, repetition, readability).
- Fresh clone runs via README; CI green.

**Phase 2**
- 30-question chat set over a demo collection: ≥ 90% answers fully cited; 0 uncited numbers; out-of-library questions refused with an offer to collect/research.
- Answers in < 20 s after the chat model is loaded.
- "Make this a report" produces a run whose plan matches the chat topic.

**Phase 3**
- A second report on a related goal reuses ≥ 30% of facts from the bank and is faster; quality not lower.
- Freshness and contradiction views correct on a seeded test collection.

**Phase 4**
- Second domain: 1 report + 10 chat questions pass the Phase 1/2 checks.
- Demo script runs offline end to end.

## How we build: one phase at a time

> **v3 (2026-10-19):** work runs by milestones M1-M5 in `SCOPE.md`; the sprint, phase-doc and user-test parts below
> are history (`archive/v2.2/`). Still in force: discuss → build → test → review → log, branches, commits on OK.

Scope: `SCOPE.md` (v3). Status: `STATUS.md`. Every phase (and Phase 1 sub-phase)
runs the same loop, and the next one starts only after the gate passes.

```
 Plan ──► Tests first ──► Build ──► Run ALL tests ──► Review ──► Gate
                                        │ fail          │ finding    │ fail
                                        ▼               ▼            │
                                  ERROR_LOG entry → fix → regression test ─► back to "Run ALL tests"
```

### Steps

1. **Plan.** Re-read the phase doc in `docs/phases/`. Resolve the open
   decisions it depends on (entry in `DECISIONS.md`). Set the phase to
   `in progress` in `STATUS.md`.
2. **Tests first.** Turn the phase's test-case table into tests before the
   feature code. Name tests by ID: `test_P1b_T03_subject_size_mismatch_dropped`.
   Report-quality cases use **saved runs** (forked checkpoints, saved
   evidence files) so they are repeatable without re-reading sources.
3. **Build** only the phase scope. Ideas go to the STATUS.md backlog.
4. **Run all tests**: offline suite every time; live/model tests at the gate.
5. **Review** with `REVIEW_CHECKLIST.md` plus the phase's review items, a
   code-review pass, and **reading one real report end to end**.
6. **Gate.** Exit criteria met, blocking user tests passed, no open
   Critical/High errors for the phase, Results section filled in, `STATUS.md`
   updated, measurements in `EVALS.md`, sprint log in `CASE_STUDY.md`.
7. Every failure or finding → `ERROR_LOG.md` → fix → regression test.

### Branches

One branch per phase (`phase-1a0`, `phase-1a`, …), merged into `main` at the phase gate, so `main` always holds a passed gate.

### Testing split: test everything possible

| Who | Tests | Where tracked |
|---|---|---|
| 🤖 Claude | Everything automatable or scriptable: unit, integration, golden, adversarial, budget, performance, live Ollama runs, API calls, dashboard end-to-end (Playwright, headless), lint, type check, secret scan, fresh-clone install; independent second labels on evals | Test files by ID; results in phase Results and `EVALS.md` |
| 🧑 User | Human judgement (blind scoring, labels), real daily use, UI feel, machine (RAM, power), accounts (keys), decisions, fresh-eyes reading | `docs/USER_TESTS.md` (status + notes) |

A blocking user test must pass before its sprint gate. A failed user test
gets an ERROR_LOG entry like any other failure.

### Severity

| Level | Meaning in this project | Gate rule |
|---|---|---|
| Critical | A wrong claim presented as supported (wrong subject, stitched numbers, invented number, "established" without two agreeing sources); data loss in the library/vault; secret leaked | Blocks the gate |
| High | In-scope feature broken; run crashes or hangs on a realistic goal; silent truncation; a gap hidden instead of stated | Blocks the gate |
| Medium | Works but degraded: slow beyond estimate, weak prose, confusing message, edge case with a clear warning | Passes only if listed in Results with an owner |
| Low | Cosmetic, wording | Does not block |

### Test types

| Type | Proves | Example |
|---|---|---|
| Unit | One function | Subject check rejects "4B" when the passage says 17B |
| Golden (saved evidence) | Output on fixed evidence meets the bar | Forked SLM run: no stitched numbers in the decision |
| Integration | Graph flow | Plan → approve → read (Send) → select → write → report saved |
| Adversarial | Bad input fails safely | Off-goal source, empty library, Ollama down, garbled PDF |

## LangChain / LangGraph: what to use for scope v2 / v2.1

Reviewed 2026-10-12 against the current docs (docs.langchain.com) and the
installed versions: langchain 1.4.2, langchain-core 1.6.4, langgraph 1.2.12,
langchain-ollama 1.1.0, langgraph-cli 0.4.32. `langgraph-checkpoint-sqlite`
3.1.1 (not yet a dependency) was inspected directly.

**Today the research graph uses only `StateGraph` + `interrupt`.** Retries,
stop, run records, per-run options and JSON parsing are hand-written. Several
open bugs (globals, options lost on resume, retries vs timeouts) map onto
built-in features.

Principle: **keep the research pipeline an explicit graph** (bounded,
checked steps); **use an agent only for chat** (open-ended conversation).
Adopt a framework feature only where it removes our own code or a known bug.

---

### 1. Research pipeline (Phase 1): LangGraph Graph API

| Feature | API | Use for | Scope items / bugs |
|---|---|---|---|
| **Send (map-reduce)** | `from langgraph.types import Send`; conditional edge returns `[Send("read_question", {...}) for q in questions]`; results via `Annotated[list, operator.add]` | One isolated reading task per question; checkpointed per task, so a resume skips finished questions (pending writes kept) | P1.2, isolation |
| **Subgraph** | compiled graph added as a node | "Read one question" = retrieve → extract → verify → subject check → select, testable on its own | P1.8, P1.9, P1.11 |
| **defer=True** | `builder.add_node("select", fn, defer=True)` | Selection waits until all question branches finish | P1.11 |
| **max_concurrency** | config `{"max_concurrency": 1}` | One model call at a time on one GPU (Send still gives structure + resume) | memory safety |
| **RetryPolicy** | `from langgraph.types import RetryPolicy`; `add_node(..., retry_policy=RetryPolicy(max_attempts=3, retry_on=...))` | Replace hand-written retries; `retry_on` = connection errors only, **not** timeouts (keeps DECISIONS rule) | P1.19 |
| **CachePolicy + SqliteCache** | `from langgraph.types import CachePolicy`; `compile(cache=...)` (`langgraph.cache.memory.InMemoryCache`; SqliteCache exists, path to confirm) | Cache extraction/verification per (passage hash, question, model, prompt version): re-runs, resumes, model tests and Phase 3 reuse skip repeated hours | P1.10, P3.2 |
| **Runtime context** | `StateGraph(State, context_schema=RunOptions)`; node `runtime: Runtime[RunOptions]` | Per-run options (limits, collection, models) without globals or state pollution | P1.19 (per-run state), options-lost-on-resume |
| **Command** | `Command(update=..., goto="revise")` | Critique → revise loop with a round counter; routing after checks | P1.13 |
| **interrupt** | already used | Clarify, plan + collection-rule approval, optional exclude list (v2.1 replaces source ticking) | P1.18 (built) |
| **Durability** | `durability="sync"` on stream/invoke | Multi-hour runs: persist before each step | reliability |
| **Time travel / fork** | `get_state_history(config)`; invoke with `checkpoint_id`; `update_state(..., as_node=...)` | **Model test**: fork one saved run at the writing step and run each candidate model on identical evidence; re-write a report with new limits without re-reading | section 9, P1.1 |
| **Custom streaming** | `from langgraph.config import get_stream_writer`; `writer({...})`; `stream_mode="custom"` (also `tasks`) | Live progress to the dashboard from inside nodes; run record keeps one writer | P1.19 (run record two writers) |
| **Encrypted checkpoints** | `EncryptedSerializer.from_pycryptodome_aes()` (`LANGGRAPH_AES_KEY`) | Optional; useful for client demos with sensitive libraries | later |

Note: under `langgraph dev` the server manages the checkpointer
(`.langgraph_api/`). Standalone runs and tests use
`langgraph.checkpoint.sqlite.SqliteSaver` (package
`langgraph-checkpoint-sqlite`).

#### Model calls

| Feature | Use for | Note |
|---|---|---|
| `ChatOllama.with_structured_output(Schema, method="json_schema")` | Fact extraction into the structured fact model (core + AI/ML fields); critique output; decision steps | Today: plain `format="json"` + manual parsing. Schema-constrained output removes a class of parse failures. **Verify with gemma4:26b in the model test** (the structured-output doc does not list Ollama explicitly; langchain-ollama supports schema `format`) |
| Thinking on/off per call (`reasoning` option in langchain-ollama) | Thinking only for the decision step | Verify parameter name on 1.1.0 |
| One `num_ctx` (32k) for every research call | Model loads once | Changing `num_ctx` reloads the model |

### 2. Chat with the library (Phase 2): LangChain v1 agent + middleware

`from langchain.agents import create_agent`, tools as `@tool` functions,
fast chat model, `SqliteSaver` checkpointer, one thread per chat (P2.7).

**Tools:** `search_passages(query, collection)`, `search_facts(query,
filters)`, `open_source(source_id)`, `collection_coverage(collection)`,
`start_report(goal, collection)`.

**Built-in middleware (`langchain.agents.middleware`):**

| Middleware | Use for |
|---|---|
| `HumanInTheLoopMiddleware(interrupt_on={"start_report": ...})` | Confirm before starting a multi-hour report (P2.6) |
| `ModelCallLimitMiddleware(run_limit=...)`, `ToolCallLimitMiddleware(...)` | Runaway-loop guard per turn |
| `ContextEditingMiddleware()` (`ClearToolUsesEdit`) | Drop old retrieved passages so a small context stays usable |
| `SummarizationMiddleware(model=..., trigger=..., keep=...)` | Long conversations on a small context |
| `ToolErrorMiddleware`, `ModelRetryMiddleware` | Tool failures become messages; transient Ollama errors retried |
| **Custom middleware** (`after_model` hook) | **Our rules in code**: every claim cited, every number found in a retrieved passage/fact, coverage statement present; otherwise one rewrite request, then a safe reply (P2.3-P2.5) |

Not needed: `LLMToolSelectorMiddleware` (5 tools), `ProviderToolSearchMiddleware`
(Anthropic/OpenAI only), shell/filesystem middleware.

**Agentic RAG pattern** (docs tutorial): grade retrieved passages for
relevance (structured yes/no), rewrite the query and retry once when they
miss, then answer. Use it inside `search_passages`, or as a middleware step,
so thin retrieval leads to a rewrite or an honest "the library doesn't cover
this", not a weak answer.

**Streaming:** `stream_mode="messages"` for tokens in the chat UI.

**Report hand-off:** `start_report` creates a run of the `deep_research`
graph through the LangGraph SDK (already served by `langgraph dev`), seeded
with the chat's goal and collection.

| Need | Recommendation | Why |
|---|---|---|
| Passage search (hybrid FTS5 + vectors, namespaces) | **Keep our own `knowledge.py`** | Works, tested, has BM25 + vectors; LangGraph stores have no keyword search |

| Option | Why not |
|---|---|

| Functional API | Graph API fits; one style across the codebase |

## Review checklist (every phase)

Any "no" becomes an ERROR_LOG entry.

### Claim correctness
- [ ] Every claim names its real subject as the source does (system, size, stage); the check compares fields, not prose.
- [ ] Every number traces to exactly one fact; no sentence mixes numbers from different sources unless labelled synthesis.
- [ ] Labels follow the rules: established = ≥2 agreeing documents; single source; synthesis; inference.
- [ ] Gaps are stated in the report and in chat; nothing is filled from general model knowledge.
- [ ] Checks test meaning (subject, support), not only form (verbatim quote, JSON shape).
- [ ] A gate looks at what was actually written, not only at what evidence existed.
- [ ] A prompt fix is checked on a goal it was not tuned on (held-out goal), not only on the failing one.

### Budgets and limits
- [ ] Every prompt has a token budget and stays within it (logged).
- [ ] Nothing is cut silently: collected / read / used counts and not-read / not-used lists in the run log and report.
- [ ] Run limits come from configuration (runtime context), not constants or globals.

### Robustness
- [ ] Ollama down / slow / out of memory gives a clear message, never a silent pass or hang.
- [ ] Resume after crash or Stop continues from the last checkpoint without redoing finished work.
- [ ] Timeouts are not retried; connection errors are (RetryPolicy).
- [ ] Messy inputs tested: garbled text, scanned PDFs, duplicate versions, off-goal sources.

### Library and data
- [ ] Nothing in the library or vault is deleted (removal moves to `.removed`).
- [ ] Facts and sources are stored with provenance (source, passage, run, model, prompt version).
- [ ] Collections stay separate; a run or chat only uses its collection unless told otherwise.

### Design discipline
- [ ] Only the phase scope was built.
- [ ] Framework features used where FRAMEWORK_FIT.md says; no new hand-rolled version of a built-in.
- [ ] Research stays an explicit graph; agent loops only in chat.
- [ ] Local only: no cloud calls by default (LangSmith off unless explicitly enabled).

### Tests and docs
- [ ] All phase test cases exist and pass; the full offline suite passes.
- [ ] One real report (or chat transcript) read end to end by a person.
- [ ] Everything automatable was tested by Claude (live model, API, Playwright where relevant), not left to the user.
- [ ] Blocking user tests in USER_TESTS.md passed; failures logged.
- [ ] STATUS.md, phase Results, DECISIONS.md, EVALS.md, CASE_STUDY.md sprint log updated.
