## Research Desk: final scope (proposed for lock, 2026-10-03)

> **Superseded for planning by [`SCOPE.md`](../SCOPE.md) v2 (2026-10-12) and [`STATUS.md`](../STATUS.md).** Kept as history; open items from here are carried into the phase docs and `ERROR_LOG.md`.

This document defines what we build to finish the research assistant, what we do not build, and how we know it is done.
After it is locked, only items marked MUST are built for v1.0; new ideas go to the backlog at the end.
It replaces the planning parts of `next-steps.md`. History stays in `DECISIONS.md`, `EVALS.md`, `closeout-review-2026-10-01.md`.

### 1. The product in three sentences

You give a goal. The assistant plans the research with you, reads a **bounded, curated** set of sources on your own machine, and
writes a magazine-style report in which every claim traces to a quote you can check, is labelled by how strong its evidence is, and
**says plainly when it cannot answer**. Everything runs locally (Ollama, no paid APIs) for one user on an 8 GB-GPU class laptop.

Out of scope as a product: multi-user, accounts, cloud hosting, paid APIs, mobile app, agent that browses on its own.

### 3. Principles

1. **Stay on the goal.** Only the user's own words steer the research; the assistant's questions never become requirements.
2. **Read less, better.** A bounded reading budget per question, primary sources first. No limit on candidates you may see and tick.
3. **Compress, don't dump.** Every question produces a short cited *finding*; chapters are written from findings, not from 40 loose facts.
4. **A claim names its real subject.** A fact must say what system it is about, as the source does, never the question's framing.
5. **A number comes from one fact.** No sentence mixes figures from different sources; stitched synthesis is labelled as synthesis.
6. **Say "cannot" before spending an hour, and again in the report.** Coverage check, gap notes, gap report (built).

### 4. The pipeline (final shape)

```
Goal -> clarify (<=4 scope questions, no library) -> plan (<=6 questions; options become questions; scope filter)
     -> coverage check -> YOU approve (+ choose what to collect)
     -> discover -> YOU tick sources (papers apart from web; reading budget applies later)
     -> collect -> index
     -> READ, per question, in isolation:  retrieve (k=8) -> extract facts -> verify (quote, support, on-topic for question AND goal,
                                           claim fidelity) -> dedupe -> select best 12 -> FINDING (3-5 cited sentences)
     -> WRITE: chapter from findings -> decision chapter (options, criteria, for/against, choice) -> summary from the decision
     -> VERIFY: number provenance, label computation, evidence gate, one-recommendation check
     -> report (reader, evidence in the margin) + run record
```

#### Context management (the techniques we adopt)

| # | Technique | Status |
|---|---|---|
| 1 | Isolation: each question retrieves and extracts in its own context (as deepagents sub-agents do) | built |
| 2 | Retrieval cap: 8 passages per question, at most 3 per document | built |
| 3 | **Reading budget:** about 6-8 best sources per question, papers first, web to fill gaps, versions and duplicates merged | MUST |
| 4 | **Selection and dedupe** before writing: best 12 facts per question (relevance, source tier, novelty); near-duplicates merged | MUST |
| 5 | **Findings layer** (compression, map-reduce): one cited finding per question; chapters and the decision read findings only | MUST |
| 6 | Offload to disk: run record, evidence file, library index, vault | built |
| 7 | **No silent truncation:** every prompt has a token budget; anything cut is reported in the run log and the report | MUST |
| 8 | **Per-role context:** planner/extractor 8k (they need about 3k), writer 16k (about +0.5 GB on gemma4:e4b) | MUST |
| 9 | Structured decision steps instead of one free-form generation | MUST |
| 10 | Reflection: after a thin question, one structured "enough? what is missing?" and one follow-up search | SHOULD |

Call budgets (tokens, input / output): extraction 3.5k / 1.2k; judge 4k / 0.3k; finding 2k / 0.6k; chapter 4k / 2k;
decision 6k / 2k (16k context); summary 2k / 0.8k. Each fits its context with room to spare; the budget is enforced in code.

### 7. Quality bar (how we know it works)

Three standing test goals (T1-T3), run before the lock and again at the end:

| Goal | Tests |
|---|---|
| T1: in-coverage (RAG chunking, on the demo corpus) | full report; at least 80% of a 30-fact sample on-topic (you); no claim-fidelity violations |
| T2: out-of-coverage | short gap report, no recommendation, no invented numbers |
| T3: options (pretrain from scratch vs continue pretraining vs fine-tune, Telugu SLM) | one plan question per option; a decision chapter with criteria and a stated limit; no stitched numbers; no off-goal chapter |

Automatic checks on every report (the run fails loudly, never silently): number provenance 100%; claim-fidelity violations 0; no prompt over budget; summary/recommendation overlap under 50%; decision present when options were named.
Comparison: the current pipeline against the new one on T3, with Compare. The result is recorded in `EVALS.md` whatever it is.

### 9. Not building (the cut line)

Deliverable-aware planning (stage 6), disagreement detection, recursive crawling, merging the two collectors, auto-tuned thresholds,
an open-ended agent loop (deepagents style: it needs a strong tool-calling model, ours are 8B), returning whole pages to the model,
Tavily or any paid search, "continue the same report" merging (each continuation is a new issue, compared with Compare), multi-user,
cloud deployment, vision or audio, debate (removed earlier).

### 10. Risks

| Risk | Mitigation |
|---|---|
| The claim-fidelity gate is too strict and starves chapters | thresholds are settings; the log lists every dropped claim with the reason; tune on T1 |
| The findings layer adds one model call per question (about 6-8 per run) | small calls, on llama; measured in phase 3 |
| An 8B model still writes weak decisions | structured steps and the optional reasoner; the gap report is the honest fallback |
| Phase 2 takes longer | cut order: D4, C3, G3, G6, E6; MUST items stay |
| Memory pressure on the reference machine | doctor warns before a run; one model at a time |

1. Writer context 16k, planner/extractor 8k: **yes**.
2. Reading budget default: **8 sources per question** (still no limit on candidates shown).
3. Reasoner model: **evaluate, do not adopt yet** (SHOULD).

5. Demo corpus: **6-8 open-access papers on RAG** (the demo subject is this project's own).
6. v1.0 definition = all MUST items and the section 7 checks. Anything else is v1.1.

### Decisions (made now, so building does not stall)

1. **Sources, in order of preference:** official APIs (arXiv, Europe PMC/PubMed, OpenAlex) > your own seed URLs > general web search. Every source is tagged with where it came from and its licence/access note.
2. **Legal line:** respect `robots.txt` and each API's terms and rate limits; skip paywalled or login pages; open-access full text only; collected content stays private and is never republished.
3. **Identification:** a real user-agent with a contact email (also earns OpenAlex's polite pool).
4. **Cap:** 30-60 sources per goal.
5. **Planner temperature 0** for reproducibility (the plan currently varies between 5 and 7 sections run to run).
6. **Model roles:** llama plans and extracts, gemma writes (measured).
7. **Library location:** one knowledge base, `<vault>/.kb/library.sqlite`, created and used by both the ingest script and the graph. Current mismatch is fixed in Milestone 0.

## Deep research demo (~3 minutes)

`npm run build`, the backend must be restarted to register the `deep_research`
graph). Pre-run the goal once so the report exists in case the live run is slow
(a run takes about 11-12 minutes; narrate over the wait or cut).

**One-line pitch:** *"Give it a goal, it asks what it needs to know, shows you a
plan, then writes a long cited report from your own documents - all on local
models, nothing leaves the machine."*

1. **The problem (20s).** Open the library folder: 11 PDFs. *"A team has a pile of
   papers and policies. Nobody has time to read them all before a decision."*
2. **Enter the goal** on the **Deep Research** page: *"How should a small team
   build a reliable retrieval-augmented generation system on small local
   models?"* Click Start.
3. **It asks before it acts (30s).** The run pauses and shows clarifying
   questions. Answer two of them, leave one blank. *"It's not guessing scope. This
   is a LangGraph interrupt - the run is paused, not polling."*
4. **Plan approval (30s).** Show the sub-questions and outline; type a revision

   ran yet. The plan is the contract."*
5. **While it runs (30s).** Show the status line. Explain the pipeline in one
   breath: *"It retrieves with keyword plus vector search, extracts facts passage

   asks a second model call to confirm the passage supports it, then writes one
   section at a time."*
6. **Open the finished report (45s).** Show: the executive summary, a section with

## Deployment runbook

For whoever installs and operates this system. Everything here was exercised
during development; the troubleshooting section lists failures that actually
happened.

### What runs where
```
+------------------ host machine ------------------+
|  Ollama (models, GPU)        :11434              |
|                                                  |
|  docker compose                                  |
|   backend   LangGraph API    :2025  --- /vault   |  <- reports, notes, sources, KB (read/write)
|                                     --- /docs    |  <- your documents (read-only)
|   dashboard Next.js          :3001  --- /vault   |
+--------------------------------------------------+
```
Nothing leaves the machine: models run in Ollama, retrieval uses a local
SQLite file, and the only outbound traffic is optional (web search, LangSmith
tracing). Set `LANGCHAIN_TRACING_V2=false` and use `search_api=local_docs` for
a fully offline deployment.

### Requirements
- Windows 11 or Linux, Docker with Compose v2, Ollama on the host.
- 16 GB RAM minimum (24 GB comfortable). A GPU with 8 GB VRAM runs 8B models
  on-GPU; without a GPU everything still runs but is several times slower.
- Disk: about 10 GB for models, plus the Docling install (about 2 GB) if you
  ingest PDFs/DOCX.

### Install
```bash
ollama pull llama3.1:8b            # planner / extractor / writer default
ollama pull qwen3-embedding:0.6b   # embeddings
ollama pull gemma4:e4b             # optional: a stronger writer (see BENCHMARKS.md)

# PDF/DOCX -> markdown with tables needs Docling (heavy). Opt in at build time:
docker compose build --build-arg INSTALL_DOCLING=true

VAULT_DIR=/path/to/vault DOCS_DIR=/path/to/documents docker compose up -d
```
Dashboard: <http://localhost:3001> - API: <http://localhost:2025>.
Use `DASHBOARD_PORT=3002` if 3001 is taken.

### Load the document library
The library is one SQLite file, `<vault>/.kb/library.sqlite` (or `KB_PATH`). The graph
and every script read the same location. Each folder you ingest is its own namespace,
so adding a folder never removes another's documents, and re-running a folder only
adds, updates or removes that folder's files. Unchanged files (same content hash) are
skipped before the slow conversion step.
```bash
python scripts/ingest_library.py /path/to/documents /path/to/vault/Sources --md-out /path/to/vault/Library
```
`--md-out` also writes each converted document as markdown, so the library is browsable
in Obsidian. It must be a folder that is not itself indexed, otherwise the copies are
indexed again; `<vault>/Library` is the usual choice and is one of the default indexed
folders, which is why deep research keeps it in step automatically. Index the vault's `Sources/` (archived web pages), **not** `Research/`: the
Research notes are model-written reports, and citing them as evidence would make the
assistant cite itself.

PDFs convert with OCR off (about 20 s per paper-sized PDF on CPU); a PDF that yields
almost no text is treated as scanned and converted again with OCR automatically.

### Keeping the library growing
- **Folders:** by default the run indexes `<vault>/Sources` (archived web pages) and `<vault>/Library`
  (your PDFs plus fetched papers). Override with `library_folders` (folders separated by `;`) or
  switch off with `auto_ingest=false`. A folder's name is its namespace in the index, so two folders
  must not share a name.
- **Fetching:** `python scripts/collect.py "<question>" --max 5` or the checkbox on the Deep Research
  page. Set `CONTACT_EMAIL` so site owners can reach you (put in the User-Agent). Sources are kept only if the local model scores them 3 of 3 ("under 3" are dropped) (`fetch_min_relevance`). Each fetch writes
  `Library/<date>-<goal>/manifest.json`: read it to see what was skipped and why. Sources are limited
  to arXiv, Europe PMC open access, and URLs you supply; respect each site's terms; keep fetched
  content private.
- **Feedback:** rating buttons on each report page write `feedback_rating` / `feedback_note` into the
  report file; the planner reads the five most recent. To reset what it has learned, delete those
  lines from the reports.

### Verify it works (10 minutes)
1. `pytest tests -q` - offline suite, no models needed.
2. `python scripts/eval_retrieval.py --kb <kb>` - recall@k on your documents
   (write your own question file first; see `evals/retrieval_qa.json` for the format).
3. In the dashboard: **Deep Research** -> enter a goal -> answer the questions
   -> approve the plan -> wait for the report.

### Operate
| Task | How |
|---|---|
| Add documents | Drop files in `<vault>/Library` (indexed at the start of every deep-research run), or in `DOCS_DIR` (read-only; indexed by deep research because the compose file lists `/docs` in `LIBRARY_FOLDERS`) |
| Change the embedding model | Set `EMBEDDING_MODEL`, then `python scripts/reindex.py --rebuild` (minutes, no PDF conversion). Until then the library refuses to open with a different model |
| Back up | Copy the vault folder (reports, sources, `.kb/library.sqlite`, profile) |
| Move to another machine | Copy the vault; re-pull the models |
| Change models | `DOCKER_LOCAL_LLM`, or per role `DOCKER_PLANNER_MODEL` / `DOCKER_EXTRACTOR_MODEL` / `DOCKER_WRITER_MODEL` (blank = `LOCAL_LLM`), e.g. `DOCKER_WRITER_MODEL=gemma4:e4b docker compose up -d` |
| Run unattended | Per run: `configurable: {ask_clarifying_questions: false, require_plan_approval: false}` in the API call |
| Update | `git pull && docker compose build && docker compose up -d` |

### Troubleshooting (all of these happened)
| Symptom | Cause | Fix |
|---|---|---|
| "Ollama isn't reachable at http://localhost:11434" inside a container | Container's `localhost` is itself | Compose sets `host.docker.internal`; do not override `OLLAMA_BASE_URL` in the host `.env` (compose reads `.env` for interpolation, which once leaked the host value in) |
| Embeddings fail although chat works in Docker | `OllamaEmbeddings` ignored `OLLAMA_BASE_URL` | Fixed: the URL is passed explicitly; if you see it again, check the embedding model is pulled |
| `port is already allocated` on 3001 | Another dashboard instance (e.g. autostart) | `DASHBOARD_PORT=3002` |
| Run dies with "prediction aborted, token repeat limit reached" | Ollama aborts a degenerate generation | Calls are retried with higher temperature and repeat penalty; a call that still fails yields an empty result instead of crashing the run |
| Job killed / machine unresponsive during long runs | Memory pressure (Docling + models + other apps) | Close heavy apps; run models one at a time; `ollama stop <model>` between stages; Docker Desktop idle costs about 1 GB |
| Ollama "connection attempt failed" on `/tokenize` mid-run with qwen3:8b | Model server stalled under load | Re-run; prefer llama3.1:8b for extraction, which was the most stable |
| PDF ingest is very slow | Docling runs on CPU-only PyTorch | Expected (1-4 min/PDF); a CUDA build of PyTorch would speed it up |
| A section says "No supporting evidence" | The library really has none for that question | Add documents (or tick *Find and collect new sources first* and choose from what it finds), or narrow the goal; this is intentional, the system will not invent |
| Fetcher saved nothing | Every candidate scored under 2, or the sites blocked/limited you | Read `manifest.json` in the run's `Library/` folder: each skip has a reason (relevance, robots.txt, paywall, duplicate, too little text) |

### Security notes
- The host `.env` is never copied into images (`.dockerignore`); configuration
  reaches containers only through `docker-compose.yml`.
- Documents mount read-only. Only the vault is writable.
- Reports quote sources verbatim: if sources contain personal data, so can reports.
- There is no authentication on the dashboard or API; bind them to localhost or
  put them behind your own reverse proxy / VPN.

## Discovery questionnaire

Questions to answer with a customer **before** deploying this system. Each one
maps to a concrete configuration decision or a known limit, so the answers are
not just conversation - they change what gets built and how it is set up.

### 1. The decision behind the report
| Ask | Why it matters | Where it lands |
|---|---|---|
| What decision will a report support, and who signs off on it? | Determines the methodology (evidence review, technology comparison, landscape scan) and how much citation rigour is needed. | Goal text + clarifying answers; the plan's outline |
| Who reads it: clinicians, engineers, executives? | Sets depth and vocabulary. | Clarifying questions ("audience") |
| What does a *wrong* report cost? | Decides whether every claim must be human-verified, and how much review time to budget. | Review process; see "Limits" below |

### 2. The documents
| Ask | Why it matters | Where it lands |
|---|---|---|
| Where do the documents live (shared drive, SharePoint, email exports, EHR exports)? | The knowledge base ingests a folder; anything else needs an export step. | Ingestion runbook |
| Formats and volume (PDF/DOCX/HTML, how many, how large)? | Docling converts about 1-4 minutes per paper-sized PDF on CPU; a large backlog is an overnight job. | `scripts/ingest_library.py` |
| Scanned/image-only PDFs? | Text extraction needs OCR; slower and less reliable. Tables in scans are the hardest case. | Set expectations up front |
| How often do documents change, and are old versions superseded? | Ingestion is incremental by file hash, but it does not know a newer policy replaces an older one. | Naming/versioning convention |
| Are there documents that must *never* be mixed in one report (different tenants, patients, clients)? | One knowledge base = one retrieval scope. | One KB file per scope (`KB_PATH`) |

### 3. Data sensitivity and deployment
| Ask | Why it matters | Where it lands |
|---|---|---|
| Can documents leave the machine or network at all? | If not, this system is a fit: all models run locally via Ollama, nothing is sent to an API. | [Deployment runbook](#), air-gapped section |
| Does any document contain patient or personal data? | Reports quote sources verbatim, so PII in sources can reach a report. | De-identify before ingest, or restrict who reads reports |
| Who administers the machine, and what hardware exists (GPU, RAM)? | An 8 GB GPU runs 8B models fully on-GPU; larger models spill to CPU and slow down sharply. | Model roles (`DOCKER_PLANNER_MODEL`, `DOCKER_EXTRACTOR_MODEL`, `DOCKER_WRITER_MODEL`) |
| Is Docker permitted? Linux, Windows, or both? | Compose is the supported install; Windows also has an autostart script. | Runbook |

### 4. How they want to work with it
| Ask | Why it matters | Where it lands |
|---|---|---|
| Should the agent ask questions before starting, or run unattended? | Interrupt-based clarification and plan approval can be turned off for batch/overnight use. | per-run `ask_clarifying_questions`, `require_plan_approval` |
| How long may a run take (20 minutes, or overnight)? | Depth is bounded by time, not by cost, since models are local. | Number of sub-questions, passages per question |
| Where should reports land (Obsidian vault, shared folder, wiki)? | Reports are markdown with frontmatter, written to a vault folder. | `VAULT_PATH` |
| Who gives feedback on report quality, and how? | The system improves only from feedback that is written down. | Feedback notes in the vault (planned) |

### 5. Success criteria (agree these on day one)
- A fixed set of 20-30 real questions whose answers are known, used to measure
  retrieval recall on *their* documents (`scripts/eval_retrieval.py`).
- A sample of extracted claims labelled by their domain expert, used to measure
  how often the automatic faithfulness check agrees with a human
  (`scripts/make_faithfulness_sheet.py`, `scripts/score_faithfulness.py`).
- A time budget per report and an acceptable review effort per report.

### Limits to state plainly
- Reports are only as good as the library: with no evidence, a section says so
  instead of guessing, but a *thin* library gives thin reports.
- Claims are checked for a verbatim supporting quote and by a second model, but
  the sources themselves are not fact-checked.
- Local 8B models write competent but not exceptional prose; treat the output
  as a cited first draft for an expert, not a finished document.

## Model benchmarks

Two model-selection decisions in this project were made by measuring against
the actual prompts this graph uses, not by assumption. Scripts live in
`scripts/benchmarks/` and are runnable against your own local Ollama models -
these results are from one machine (RTX 5050, 8GB VRAM, another process
holding ~6GB of it) and will vary on different hardware, but the *method* -
test the real prompt shape, test a positive and a negative case, don't trust
a library's own claims - is the point.

### 1. Chat model (`LOCAL_LLM`)

`scripts/benchmarks/benchmark_chat_models.py` - JSON-mode query generation and
unconstrained summarization, the two prompt shapes this graph relies on most.

| Model | Query-gen | Summarize | Total | Valid |
|---|---|---|---|---|
| **llama3.1:8b** (chosen) | 10.5s | 9.6s | **20.1s** | yes |
| granite4.1:8b | 10.2s | 15.3s | 25.5s | yes |
| qwen3:8b | 16.4s | 14.5s | 30.9s | yes |
| ministral-3:8b | 13.8s | 19.9s | 33.7s | yes |
| deepseek-r1:8b (tutorial's suggested model) | 21.9s | 15.0s | 36.9s | yes |
| qwen3.5:latest | 18.7s | 25.5s | 44.2s | yes |
| qwen3.5:4b (original default) | 41.4s | 26.7s | 68.1s | yes |

All seven produced valid, non-empty output - this was purely a speed decision.
`llama3.1:8b` was ~3.4x faster than the model it replaced, with no quality
tradeoff on spot-check. Notably the tutorial's own suggested model
(`deepseek-r1:8b`) wasn't the fastest despite being an R1-style "thinking"
model this repo's `strip_thinking_tokens` machinery was clearly built around.

### 2. Comparison mode's multi-tool-calling reliability

`scripts/benchmarks/benchmark_tool_calling.py` - comparison mode's
`plan_research` node depends on a model reliably calling one tool multiple
times in a single turn when it detects a comparison, and exactly once when it
doesn't. This needed empirical validation, not assumption - the risk (per
`open_deep_research`'s own docs) is that small local models are less

### 3. Deep-research model roles

`scripts/run_deep_report.py` with each model in all three roles (planner,
extractor, writer) on the same goal and library, before the retrieval fixes
(v2 pipeline; the qwen3 run finished, a second attempt crashed on an Ollama
`/tokenize` connection error, so its numbers are from the first run).

| model | run time | verified facts | cited facts | empty sections | papers used | verdict |
|---|---|---|---|---|---|---|
| llama3.1:8b | ~9 min | 56 | 45 | 0 | 6/11 | fastest, most stable extractor |
| qwen3:8b | ~3-4 min per question (vs ~1 for llama) | n/a | 46 | 0 | 7/11 | most on-topic prose, several times slower, cites ranges like `[E6-E9]` |

Conclusion drawn from measurement: **extract with llama, write with gemma.**
With the v5 pipeline, that mix produced ~21% more body text (2,619 vs 2,165
words) at the same number of cited facts, for about 8% more time
(12.0 vs 11.1 minutes). qwen3's slowness and the tokenizer crash ruled it out
as a default despite good prose. Note the caveat: one goal, one run per cell;
planner variance is large enough that small differences (5-10%) are within noise.
