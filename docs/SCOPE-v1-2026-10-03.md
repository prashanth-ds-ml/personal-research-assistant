## 1. The product in three sentences

You give a goal. The assistant plans the research with you, reads a **bounded, curated** set of sources on your own machine, and
writes a magazine-style report in which every claim traces to a quote you can check, is labelled by how strong its evidence is, and
**says plainly when it cannot answer**. Everything runs locally (Ollama, no paid APIs) for one user on an 8 GB-GPU class laptop.

Out of scope as a product: multi-user, accounts, cloud hosting, paid APIs, mobile app, agent that browses on its own.

## 3. Principles

1. **Stay on the goal.** Only the user's own words steer the research; the assistant's questions never become requirements.
2. **Read less, better.** A bounded reading budget per question, primary sources first. No limit on candidates you may see and tick.
3. **Compress, don't dump.** Every question produces a short cited *finding*; chapters are written from findings, not from 40 loose facts.
4. **A claim names its real subject.** A fact must say what system it is about, as the source does, never the question's framing.
5. **A number comes from one fact.** No sentence mixes figures from different sources; stitched synthesis is labelled as synthesis.
6. **Say "cannot" before spending an hour, and again in the report.** Coverage check, gap notes, gap report (built).

## 4. The pipeline (final shape)

```
Goal -> clarify (<=4 scope questions, no library) -> plan (<=6 questions; options become questions; scope filter)
     -> coverage check -> YOU approve (+ choose what to collect)
     -> discover -> YOU tick sources (papers apart from web; reading budget applies later)
     -> collect -> index
     -> READ, per question, in isolation:  retrieve (k=8) -> extract facts -> verify (quote, support, on-topic for question AND goal,
                                           claim fidelity) -> dedupe -> select best 12 -> FINDING (3-5 cited sentences)
     -> WRITE: chapter from findings -> decision chapter (options, criteria, for/against, choice) -> summary from the decision
     -> VERIFY: number provenance, label computation, evidence gate, one-recommendation check
     -> report (reader, evidence in the margin) + run record
```

### Context management (the techniques we adopt)

| # | Technique | Status |
|---|---|---|
| 1 | Isolation: each question retrieves and extracts in its own context (as deepagents sub-agents do) | built |
| 2 | Retrieval cap: 8 passages per question, at most 3 per document | built |
| 3 | **Reading budget:** about 6-8 best sources per question, papers first, web to fill gaps, versions and duplicates merged | MUST |
| 4 | **Selection and dedupe** before writing: best 12 facts per question (relevance, source tier, novelty); near-duplicates merged | MUST |
| 5 | **Findings layer** (compression, map-reduce): one cited finding per question; chapters and the decision read findings only | MUST |
| 6 | Offload to disk: run record, evidence file, library index, vault | built |
| 7 | **No silent truncation:** every prompt has a token budget; anything cut is reported in the run log and the report | MUST |
| 8 | **Per-role context:** planner/extractor 8k (they need about 3k), writer 16k (about +0.5 GB on gemma4:e4b) | MUST |
| 9 | Structured decision steps instead of one free-form generation | MUST |
| 10 | Reflection: after a thin question, one structured "enough? what is missing?" and one follow-up search | SHOULD |

Call budgets (tokens, input / output): extraction 3.5k / 1.2k; judge 4k / 0.3k; finding 2k / 0.6k; chapter 4k / 2k;
decision 6k / 2k (16k context); summary 2k / 0.8k. Each fits its context with room to spare; the budget is enforced in code.

Tight memory on this machine today is uTorrent Web (about 5 GB), not the project.

## 7. Quality bar (how we know it works)

Three standing test goals (T1-T3), run before the lock and again at the end:

| Goal | Tests |
|---|---|
| T1: in-coverage (RAG chunking, on the demo corpus) | full report; at least 80% of a 30-fact sample on-topic (you); no claim-fidelity violations |
| T2: out-of-coverage | short gap report, no recommendation, no invented numbers |
| T3: options (pretrain from scratch vs continue pretraining vs fine-tune, Telugu SLM) | one plan question per option; a decision chapter with criteria and a stated limit; no stitched numbers; no off-goal chapter |

Automatic checks on every report (the run fails loudly, never silently): number provenance 100%; claim-fidelity violations 0; no prompt over budget; summary/recommendation overlap under 50%; decision present when options were named.
Comparison: the current pipeline against the new one on T3, with Compare. The result is recorded in `EVALS.md` whatever it is.

## 9. Not building (the cut line)

Deliverable-aware planning (stage 6), disagreement detection, recursive crawling, merging the two collectors, auto-tuned thresholds,
an open-ended agent loop (deepagents style: it needs a strong tool-calling model, ours are 8B), returning whole pages to the model,
Tavily or any paid search, "continue the same report" merging (each continuation is a new issue, compared with Compare), multi-user,
cloud deployment, vision or audio, debate (removed earlier).

## 10. Risks

| Risk | Mitigation |
|---|---|
| The claim-fidelity gate is too strict and starves chapters | thresholds are settings; the log lists every dropped claim with the reason; tune on T1 |
| The findings layer adds one model call per question (about 6-8 per run) | small calls, on llama; measured in phase 3 |
| An 8B model still writes weak decisions | structured steps and the optional reasoner; the gap report is the honest fallback |
| Phase 2 takes longer | cut order: D4, C3, G3, G6, E6; MUST items stay |
| Memory pressure on the reference machine | doctor warns before a run; one model at a time |
